1 Optimización en sistemas financieros

En una aplicación bancaria que procesa transacciones en tiempo real, ¿qué estrategias aplicarías para mejorar rendimiento y escalabilidad? Concurrencia, caché y patrones.

Lo primero que haría es medir. En una API de transacciones el cuello de botella casi nunca está en el código Java; suele estar en la base de datos, en transacciones demasiado largas o en llamadas externas metidas dentro de la transacción. Sin métricas de latencia (p95 y p99), throughput y errores, cualquier optimización es una apuesta.

Concurrencia

La fuente de la verdad es la base de datos. No llevaría saldos en memoria ni en un mapa compartido entre instancias. Para las operaciones que tocan un saldo usaría transacciones cortas y un mecanismo de bloqueo explícito: optimista con @Version cuando los conflictos son raros, y pesimista con SELECT ... FOR UPDATE cuando la operación es crítica y los conflictos son frecuentes. En PostgreSQL, READ COMMITTED suele ser suficiente; subir a SERIALIZABLE solo si hay una invariante que lo exija, y asumiendo que habrá que reintentar.

  • Transacciones cortas y sin HTTP a servicios externos dentro de ellas.
  • Clave de idempotencia en la operación para que un reintento del cliente no duplique el movimiento.
  • Colas (Kafka, RabbitMQ o SQS) para los picos y consumidores con concurrencia limitada, aplicando backpressure.
  • Virtual threads de Java 25 para el trabajo de I/O, pero con pools y timeouts; no lanzar hilos sin control.
  • API sin estado para escalar horizontalmente, y pool de conexiones dimensionado al tamaño real de la base de datos.

Si la base de datos es el límite, separaría el modelo de lectura del de escritura, añadiría réplicas para consultas y particionaría por cliente o por fecha. No metería microservicios antes de tener el problema: cambiar complejidad de código por complejidad operativa no suele salir bien.

Caché

Cachearía lo que se puede quedar viejo unos segundos: tipos de cambio, catálogos, resúmenes o el estado de una solicitud. El saldo disponible no lo trataría como un dato cacheado de verdad; como mucho, una vista de lectura con TTL corto e invalidación explícita al escribir. Caffeine va bien para caché local; Redis si hay varias instancias y necesito compartirla. Patrón cache-aside, TTL corto y cuidado con el stampede cuando expira una entrada muy consultada.

En este proyecto usé Caffeine para los listados de préstamos, con TTL de 30 segundos y evicción al crear o decidir. Para saldos no lo haría: un saldo cacheado que no se invalida a tiempo es un problema de negocio, no de rendimiento.

Patrones

CQRS y outbox cuando el volumen los justifica; saga para flujos entre servicios; circuit breaker y timeouts para dependencias externas. Empezaría con un monolito modular bien separado por dominio. Los patrones se añaden cuando resuelven un problema medido, no antes. Para notificaciones en tiempo real usaría SSE o WebSocket, pero como canal de aviso, no como fuente de verdad del saldo.

2 Seguridad en APIs financieras

¿Cómo protegerías una API con información sensible de cuentas contra inyección SQL, CSRF, XSS y otros ataques comunes?

Defensa en profundidad. Ninguna capa sola alcanza, y la seguridad real está en el backend; lo que haga el frontend es experiencia de usuario, no control de acceso.

Inyección SQL

Con JPA o consultas parametrizadas el problema casi desaparece. La regla es no concatenar nunca entrada del usuario en SQL, ni siquiera para un ORDER BY: si el ordenamiento es dinámico, se valida contra una lista blanca. El usuario de base de datos de la aplicación no debe ser superusuario, solo tener permisos sobre su esquema. Las migraciones las maneja Flyway y las consultas nativas usan parámetros con nombre, no ${...}.

CSRF

Con un access token en la cabecera Authorization el navegador no lo envía solo, así que el CSRF clásico baja bastante. El riesgo aparece con la cookie de refresh: esos endpoints sí necesitan token CSRF, con CookieCsrfTokenRepository y la cabecera X-XSRF-TOKEN. La cookie va HttpOnly, Secure, SameSite=Lax y con un Path acotado. En Angular se configura con withXsrfConfiguration.

XSS

Angular escapa las interpolaciones por defecto. El problema llega cuando se usa innerHTML, bypassSecurityTrustHtml o se pinta contenido de terceros. Ahí hay que sanitizar en el servidor y evitar confiar en el cliente. Una CSP restrictiva (script-src 'self'), X-Content-Type-Options: nosniff y una Referrer-Policy ayudan. Y algo que mucha gente pasa por alto: el access token no va en localStorage; si hay XSS, se lo llevan. En memoria y el refresh en cookie HttpOnly.

El resto

  • Autorización en el backend con @PreAuthorize y comprobación de propiedad del recurso, no solo del rol. Un usuario no debe poder leer la cuenta de otro cambiando un id.
  • JWT de vida corta, refresh rotatorio, hash del refresh en base de datos y revocación si se detecta reutilización.
  • Rate limit y bloqueo progresivo en login, sin revelar si el correo existe.
  • TLS y HSTS; CORS con orígenes exactos, nunca * con credenciales.
  • Secretos en variables de entorno o en el gestor del proveedor, nunca en el repositorio.
  • Validación con Bean Validation y DTOs de entrada para evitar mass assignment; errores sin stacktrace ni detalles internos.
  • Auditoría de accesos y operaciones, sin loguear datos sensibles, y escaneo de dependencias en CI.
  • Idempotencia y límites de tamaño en operaciones de dinero.

Al final, lo que busco es que el fallo de una capa no se convierta en el fallo de todo: validar en el borde, autorizar en cada recurso, no confiar en el cliente y reducir el impacto cuando algo se rompe. La seguridad no es una anotación suelta.

3 Transacciones en sistemas distribuidos

En un sistema bancario distribuido, ¿cómo implementarías consistencia y manejo de errores en una API que procesa transferencias entre cuentas de diferentes servicios?

Lo primero es intentar que la transferencia no sea distribuida. Si las dos cuentas viven en la misma base de datos o en el mismo servicio, una transacción local con bloqueo de filas resuelve el problema sin añadir complejidad. Si de verdad son servicios distintos, no usaría una transacción 2PC: acopla la disponibilidad de todos y en la práctica es difícil de operar.

Usaría una saga con un orquestador y una máquina de estados. La transferencia se crea en PENDING con una clave de idempotencia; se retiene el dinero en la cuenta de origen; se acredita en la de destino; y solo entonces se confirma. Si un paso falla, se compensa lo anterior: liberar la retención o revertir el crédito. Cada paso tiene que ser idempotente, porque los reintentos van a ocurrir.

  • Tabla de estado de la transferencia y de sus pasos, con transiciones claras.
  • Outbox transaccional para publicar eventos después del commit; así no hay doble escritura entre la base y el broker.
  • Consumidores idempotentes, deduplicando por id de evento, y reintentos con backoff, timeout y cola de mensajes fallidos.
  • Reconciliación periódica contra el ledger. Al final, la verdad contable es el ledger de doble entrada, no el saldo que muestra una pantalla.
  • Observabilidad con trazas y un id de operación que aparezca en logs, respuesta y soporte.

La consistencia es fuerte dentro de cada servicio y eventual entre servicios. No se puede prometer “exactamente una vez” de punta a punta; se trabaja con entrega al menos una vez y consumidores idempotentes. Los errores se traducen a códigos claros: 409 si hay conflicto de estado, 422 si incumple una regla de negocio, 503 si una dependencia no está disponible. Y nada de devolver un 500 genérico que no le dice nada a quien opera el sistema.

En este proyecto la aprobación de un préstamo es una sola transacción con @Transactional y una transición PENDING → APPROVED/REJECTED. Si mañana el desembolso lo hiciera otro servicio, lo resolvería con outbox y saga, no con una llamada HTTP dentro de la transacción.

4 Pruebas unitarias y de integración

¿Cómo diseñarías una suite de pruebas para asegurar una API bancaria? ¿Qué herramientas usarías?

Depende de lo que duela, pero la base es la misma: muchas pruebas rápidas de reglas de negocio y una capa más pequeña de pruebas de integración que arrastren infraestructura real. En un banco no me interesa solo que el endpoint responda 200; me interesa que no se pueda retirar más de lo que hay, que un usuario no vea la cuenta de otro y que una decisión no se aplique dos veces. He visto suites con mucha cobertura y pocos casos de negocio; prefiero menos tests, pero que duelan cuando algo se rompe.

Unitarias

JUnit 5 con Mockito y AssertJ para el dominio y los servicios, sin levantar Spring. Casos felices, límites, estados inválidos, permisos, idempotencia y errores. Inyectaría un Clock para no depender de la hora real y evitar pruebas que fallan en enero.

Integración

@SpringBootTest con MockMvc o TestRestTemplate, y Testcontainers con PostgreSQL real. H2 es cómodo, pero esconde diferencias de SQL, constraints y bloqueos que sí aparecen en producción. Así valido Flyway, el mapeo de JPA y las migraciones de verdad. La matriz de seguridad es obligatoria: anónimo, usuario autenticado, admin y usuario dueño frente a otro usuario. También los errores de validación y el formato de las respuestas.

  • Pruebas de concurrencia en las operaciones críticas: dos decisiones simultáneas sobre el mismo préstamo, dos transferencias que compiten por el mismo saldo.
  • Pruebas de contrato si hay varios consumidores: Pact o Spring Cloud Contract.
  • E2E con Playwright o Cypress para el recorrido crítico: login, solicitar, aprobar y ver el estado.

Frontend

Vitest con TestBed, HttpTestingController para servicios e interceptores, y pruebas de guards y formularios reactivos. Para el flujo completo, Playwright. No probaría cada detalle visual; sí las validaciones, los estados de error y que el rol admin no vea las acciones de decisión si no le corresponden.

En CI correría todo en cada PR, con cobertura enfocada en el dominio (no perseguiría un 100% global), análisis estático y escaneo de dependencias. Las pruebas tienen que ser deterministas: nada de sleep, datos aislados y Awaitility para lo asíncrono.

En este repositorio tengo pruebas unitarias del servicio de préstamos y una prueba de API con JWT firmado y Testcontainers. Para el frontend, build, lint y Vitest para la lógica que lo merece.

5 Front-end: estado y autenticación

En una aplicación bancaria que muestra el saldo de las cuentas, ¿cómo gestionarías el estado y la autenticación en el front-end, garantizando seguridad y coherencia?

El backend es la fuente de verdad. El frontend pinta, valida y da feedback, pero no decide cuánto dinero hay ni quién puede aprobar. Eso cambia la forma de gestionar el estado: guardo poco y lo guardo con fecha de caducidad.

Estado

En Angular 22 uso servicios con signals. Un servicio de sesión guarda el usuario y su rol; los componentes derivan lo que necesitan con computed. Para este tamaño no metería NgRx: añade ceremonia sin resolver nada que no haga un servicio con signals. El saldo no lo dejaría como estado global permanente; lo pediría al entrar en la vista, al volver a la pestaña y después de cualquier operación. Si hay SSE o WebSocket, el evento invalida y se vuelve a pedir; el push es un aviso, no la verdad.

Para coherencia, las operaciones de dinero no las haría optimistas. Esperaría la respuesta del servidor, deshabilitaría el botón mientras se envía y manejaría un 409 de conflicto enseñando el estado actualizado. Un “ya está hecho” que luego no se confirma es peor que un segundo de espera.

Autenticación

Access token de vida corta en memoria, refresh token en cookie HttpOnly, Secure y SameSite=Lax. Nada de localStorage. El interceptor añade la cabecera Bearer y, si recibe un 401, hace un refresco single-flight y reintenta la petición una vez. Varias peticiones a la vez no deben disparar cinco refrescos. El logout revoca el refresh en el servidor y limpia el estado local.

Los guards de Angular son para la experiencia: evitar que alguien entre a una pantalla que no le corresponde y conservar el returnUrl. La autorización de verdad está en el backend con @PreAuthorize y comprobación de propiedad. Cualquiera puede abrir las DevTools y saltarse un guard.

Añadiría CSP, no pondría tokens ni datos de cuenta en logs o URLs, y protegería con CSRF los endpoints que usan la cookie. El access token en memoria se pierde al recargar; por eso al arrancar se intenta restaurar la sesión con el refresh.

6 Spring Boot

a. ¿Qué pasa internamente con @SpringBootApplication?

Es una anotación compuesta. Junta @SpringBootConfiguration (que a su vez es @Configuration), @EnableAutoConfiguration y @ComponentScan. Cuando llamas a SpringApplication.run, se crea el contexto de aplicación, se prepara el Environment con perfiles, propiedades y variables de entorno, se cargan las definiciones de beans y se escanea el paquete de la clase principal y sus subpaquetes.

Después entra la auto-configuración: Spring Boot lee las clases declaradas en META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports y las va filtrando con condiciones como @ConditionalOnClass, @ConditionalOnMissingBean o @ConditionalOnProperty. Las que aplican registran beans; las que no, se descartan. Al final arranca el servidor embebido (Tomcat en una app MVC), se publican eventos y se ejecutan los ApplicationRunner o CommandLineRunner.

Lo que suele morder es mover la clase principal fuera del paquete raíz: el @ComponentScan deja de encontrar tus beans. Y como las auto-configuraciones se aplican después de los beans del usuario, si defines uno propio, la de Boot se retira sola. Esa es la base de poder sobrescribir sin pelear.

b. Ciclo de vida de un bean

El contenedor registra la definición, instancia el bean (normalmente por constructor), inyecta dependencias, llama a BeanNameAware y BeanFactoryAware si aplican, ejecuta los BeanPostProcessor antes de la inicialización, luego @PostConstruct, InitializingBean.afterPropertiesSet() o el initMethod, y después los BeanPostProcessor de después de la inicialización. Ahí es donde Spring envuelve el bean en proxies para AOP, transacciones o seguridad. Al cerrar el contexto, @PreDestroy, DisposableBean.destroy() o el destroyMethod.

Los scopes por defecto son singleton; prototype se crea cada vez y el contenedor no lo destruye; request y session existen en aplicaciones web. Para intervenir uso @PostConstruct para validar configuración, @Bean(initMethod/destroyMethod) para recursos externos, un BeanPostProcessor para proxies o cross-cutting, y un ApplicationListener para reaccionar a eventos. No metería lógica pesada en el constructor: si necesita la base de datos o validar algo, mejor @PostConstruct o un runner.

c. Personalizar la auto-configuración sin romper la convención

Sigo un orden: primero propiedades, luego un bean propio, después un customizer, y solo al final excluir. Casi todo se resuelve con @ConfigurationProperties o con un bean que hace que la auto-configuración se retire por @ConditionalOnMissingBean. Para detalles del servidor o de seguridad, un WebServerFactoryCustomizer o mi propio SecurityFilterChain; para una librería interna, una auto-configuración con @AutoConfiguration, condiciones y @AutoConfigureBefore/After.

En este proyecto hay varios ejemplos: el JwtEncoder/JwtDecoder propios, el CacheManager de Caffeine, las propiedades de CORS y una cadena de seguridad con las reglas de la API. Boot sigue aportando el resto. También toqué propiedades como spring.jpa.open-in-view=false y ddl-auto=validate, que es justo lo que espero: cambiar lo necesario de forma explícita.

Excluir una auto-configuración es el último recurso. Si tengo que excluir cinco, probablemente estoy peleando contra el framework y conviene replantear la aproximación. La convención sobre configuración no significa no tocar nada; significa que el default funcione y que lo que cambie esté acotado, documentado y probado.

Varias de estas decisiones están aplicadas en el repositorio de la prueba: JWT corto con refresh en cookie, guards en Angular, caché con evicción, transacciones en la aprobación y pruebas con Testcontainers.
