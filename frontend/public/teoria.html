1. Optimización en sistemas financieros

En una aplicación bancaria que procesa transacciones en tiempo real, ¿qué estrategia aplicarías para mejorar rendimiento y escalabilidad?

Rendimiento: Primero mediría dónde está el cuello de botella. Puede ser a nivel de frontend por malas prácticas o mala optimización, como un bucle, o a nivel de transacciones. Si hay demasiadas transacciones y el servidor ya no da para más, se necesitaría generar múltiples hilos para procesar todas las transacciones, aunque eso solo ayuda cuando el límite está en la espera de I/O y no en la CPU. Dependiendo de la estructura del proyecto, si es un Spring Boot con Java, se puede utilizar virtual threads para no mover todo el framework a Spring Reactive. Escalabilidad: Evaluaría mi base de usuarios actual y cuántas personas consumen mi aplicación. En base a eso decidiría la escala. Normal sería arrancar con un monolito, que sea un proceso, un servicio. A medida que se requieran más, ese monolito puede ser un monolito multipaquete, que dentro del monolito hayan otros servicios pero todavía están dentro del mismo monolito. Y ya si es demasiado grande se podría hacer una escala a microservicios. Igual depende de la funcionalidad de la aplicación. Concurrencia: Es más un tema de sincronización. Lo que se haría sería separar todas las acciones que se hagan a base de datos con transacciones y se harían unas consultas. Por ejemplo, si hay dos transacciones al mismo tiempo para un mismo campo, para que ese campo devuelva realmente el valor que se tenga y se resuelvan ambas transferencias con valores correctos, se utilizaría por ejemplo un bloqueo pesimista, con transacciones cortas y un orden de bloqueo consistente para no caer en deadlocks. Caché: Dependiendo de la cantidad de consultas que se hagan a la base de datos, para reducir ese volumen se optaría por ejemplo por Redis para mantener los datos en memoria RAM y hacer consultas directamente a esto y no a la base de datos, siempre que sean datos que toleran estar algo viejos; el saldo no se cachea. Patrones de diseño: Tendría que verse cómo se pretende escalar la aplicación para aplicar X o Y patrón.

2. Seguridad en APIs financieras

¿Cómo protegerías una app con información sensible de cuentas contra inyecciones SQL, CSRF, XSS y otros ataques comunes?

Inyecciones SQL y XSS: Yo creo que es más un tema de buenas prácticas que de ataques que haya que tratar uno por uno. Es importante tenerlo presente, porque se resuelve casi solo utilizándolas. Para inyecciones SQL, si se utiliza JPA, o sea si se utilizan los repositorios que ofrece Spring Boot para hacer todas las transacciones con base de datos, que no se concatenen valores en la consulta, que esos valores se pasen siempre como parámetros y que no se armen consultas con lo que llega de la API. Si se evitan esas malas prácticas que ya son conocidas se evita muy fácilmente la inyección SQL. Para ataques XSS es igual, es más que todo a nivel de malas prácticas. En el caso de Angular, Angular es muy fuerte por defecto. Para permitir que te hagan un ataque XSS es porque estás haciendo algo o estás moviendo algo a propósito que evade ya los guardarraíles que ofrece Angular por defecto, como innerHTML o bypassSecurityTrustHtml. Entonces es como evitar hacerlo. CSRF Token: Esto es más que todo cuando hay manejo de sesiones en la aplicación, entonces se necesita el token CSRF para que otro sitio no pueda usar tu sesión sin que te des cuenta, junto con SameSite y Secure en las cookies. Lo que el token no hace es proteger una cookie ya robada: contra eso está HttpOnly, que impide leerla desde JavaScript, y una CSP que corte el XSS. Entonces se necesitaría ya ahí el tema de CSRF. No es que sea un obligatorio tampoco, depende también de la aplicación.

3. Transacciones en sistemas distribuidos

En un sistema bancario distribuido, ¿Cómo implementarías consistencia y manejo de errores en una API que precise transferencia entre cuentas de diferentes servicios?

Consistencia: Lo que yo me asumiría como consistencia sería que todas las transferencias, si una transferencia falla, esa transacción se revierta y no deje ningún efecto. Eso funciona si las cuentas comparten base; si están en servicios distintos, un rollback local no deshace lo que el otro servicio ya confirmó, así que ahí necesitaría compensaciones, tipo saga, con pasos idempotentes. También con un bloqueo optimista o pesimista, si no estoy mal, me encargaría de seleccionar los datos reales de mi aplicación actual, entonces mantendría la consistencia de los valores y no quedarían duplicados en retiros ni en aumentos en caso pues que es una transferencia. Manejo de errores en una API: Es muy común que cuando se llaman otras APIs haya falsos positivos, o sea la comunicación es exitosa, se hace toda la transacción y devuelven doscientos, pero internamente en la información te dice que hay un error. Eso es porque se valida únicamente todo el proceso lógico del servicio, todo el proceso a nivel de controlador, y el servicio responde, pero realmente internamente no está dando una información acorde a ese código de respuesta. Lo mejor es erradicar el error de raíz, siempre y cuando se tenga acceso, porque hay veces se llaman a servicios de externos o de terceros que hacen estos mismos falsos positivos y ya se infiere esa deuda técnica. Se implementa un sistema de respuesta basado en la respuesta de negocio, o sea que lo que condicione el estado de esa API sea el resultado total de esa API. Entonces si es una transferencia de dinero, se tiene que validar el valor o el contenido de esa transferencia, validar si realmente contiene la información que debería responder. De esa manera se valida que no hayan falsos positivos.

4. Pruebas unitarias y de integración

¿Cómo diseñarías una suite de pruebas para asegurar una API bancaria? ¿Qué herramientas usarías?

No armaría algo muy complejo: empezaría por test unitarios de la lógica de negocio, que es lo más importante. Después haría pruebas de integración, de por ejemplo que se pruebe el controlador, la consulta y el resultado, que los tipos y el resultado sean consistentes. Utilizaría por ejemplo Mockito. Y pues tendría que hacer las integraciones, por ejemplo con test para hacer las consultas con PostgreSQL y ahí pasaría todas las validaciones. Y por ejemplo para completar flujos del uso de la aplicación.

5. Front-end: estado y autenticación

En una aplicación bancaria que muestra el saldo de las cuentas, ¿Cómo gestionarías el estado y la autenticación en el Frontend? Garantizando seguridad y coherencia.

Estado: Depende mucho, si es una aplicación bancaria debe mantenerse al día en todas las sesiones iniciadas, de la cuenta a la que se le esté haciendo la transacción o gestionando un cambio, entonces todos deben enterarse o estar al día de cualquier cambio. Si no se permiten múltiples sesiones, se puede mantener con un estado general desde la aplicación. Hay muchos tipos, se puede utilizar por ejemplo una librería para manejar el estado, pero en Angular lo que utilizaría para esos casos serían los signals y RxJS para lo asíncrono. Autenticación: Para la autenticación en el Frontend usaría un access token de corta duración en memoria y el refresh en una cookie HttpOnly, con un interceptor que añada el token y refresque una sola vez si llega un 401; los guards solo controlan la navegación y la autorización real la sigue haciendo el backend.
